# Working on specOS

Instructions for anyone — human or AI agent — writing code in this repo. This is about
*developing specOS itself*, not about `.specos/memory/project.md`, which is a separate,
runtime concept: conventions specOS auto-loads into the worker agents it spawns to build
*someone else's* project.

For what specOS does and how to run it, see [README.md](README.md). This file is about how to
change its code.

## Layout

```
src/cli/            commander wiring — one file per subcommand under commands/, registered in index.ts
src/spec/           spec ingestion: parsers/ (markdown, text), agents/ (normalizer, validator),
                     ingest.ts (clarification loop), specFiles.ts + specMarkdown.ts (specs/<id>.md)
src/orchestrator/    the task-graph runner: worktrees, review, merge, retries
src/swarm/           worker/reviewer/conflict-resolver agents + their sandboxed tools
src/harness/         state machine, guardrails (retry/backoff/circuit breaker), approval gates, audit log
src/memory/          project/swarm/feedback memory tiers injected into worker prompts
src/integrations/    git, Jira, Anthropic credentials — anything talking to the outside world
src/storage/         SQLite-backed StateStore
src/engine/          AgentProvider abstraction + the Claude Agent SDK implementation
```

Each directory is one concern. A new external integration goes under `src/integrations/<name>/`;
a new CLI command gets its own file under `src/cli/commands/`, registered in `src/cli/index.ts`.

## TypeScript / module conventions

- Strict mode, ES2022, `module`/`moduleResolution: NodeNext`. Relative imports must include the
  `.js` extension (`from "../spec/schema.js"`), even though the source file is `.ts` — NodeNext
  resolves against the compiled output's extension, not the source's.
- No linter/formatter is configured. Match the surrounding file's style (2-space indent, double
  quotes, semicolons, trailing commas in multiline literals).
- Validate at boundaries with zod (`ConfigSchema`, `SpecNodeSchema`, `ValidationResultSchema`,
  ...) — parse untrusted input (files, agent JSON responses, CLI flags) once, at the edge, then
  trust the typed value everywhere downstream. Don't re-validate internally.
- Prefer small, composable functions over classes; use a class only when there's real mutable
  state to encapsulate (`StateStore`, `SwarmMemory`, `Mutex`, agent handles).

## Code style

- Comments are rare and short — one line, explaining a non-obvious *why* (a hidden constraint, a
  workaround, a token-cost tradeoff), never a *what*. If removing a comment wouldn't confuse a
  future reader, don't write it. No multi-paragraph doc comments.
- Errors thrown at a CLI action boundary should be a plain `Error` with a message that tells the
  user what to actually do next (see any `throw new Error(...)` in `src/cli/commands/`) — they
  bubble up to `index.ts`'s single `.catch()` and print as `specos: <message>`.
- Don't add fallbacks, retries, or validation for cases that can't happen given the code that
  calls into a function — guard at the boundary (CLI flags, file parsing, agent output), trust
  internal callers.
- Agent-facing system prompts (normalizer, validator, worker, reviewer, summarizer) are the
  product's actual behavior, not incidental strings — change them deliberately, and prefer
  extending an existing agent's prompt over adding a new agent role for a small variation.

## Testing

- `vitest`, files under `test/`, no separate mocking framework — a fake `AgentProvider` whose
  `sendMessage` branches on `options.role` is the standard way to test anything that calls an
  agent (see `test/orchestrator.test.ts`, `test/ingest.test.ts`).
- Anything touching git (`worktree.ts`, merges, `commitPaths`) is tested against a *real* git repo
  in a `mkdtemp` tmp dir, not mocked — clean it up in a `finally`.
- Code that goes through the OS keychain (`keytar`) is not unit-tested directly (mirrors the
  existing Jira credential code); logic that *uses* a keychain-backed value (e.g.
  `applyStoredAnthropicKey`) is tested with the credentials module mocked via `vi.mock`.
- Before considering any change done: `npm run typecheck && npm test`. `npm run build` if you
  touched anything the compiled `dist/` output needs to reflect (the linked `specos` binary runs
  `dist/`, not `src/`).

## Keeping the CLI self-documenting

Whenever you add, rename, or change what a `specos` command does:
- Update that command's `.description()` string.
- Update `printQuickStart()` in `src/cli/banner.ts` if it's one of the first-run commands, and
  the matching assertions in `test/banner.test.ts`.
- Update `README.md` — it's the source of truth for end users; this file is for contributors.

`specos --help` / `specos <cmd> --help` are generated by Commander from the registered commands,
so those stay accurate automatically — only the quick-start banner and the description strings
themselves need manual upkeep.

## Commits

Imperative, present-tense subject line, no trailing period (`Add feedback memory and replace
spec.lock.json with per-requirement Markdown specs`, not `Added feedback memory.`). Body explains
*why*, in a short bulleted list, when the change isn't self-explanatory from the subject alone.
